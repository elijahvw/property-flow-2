# Property Flow project guidance

Applies to this repository. This is the canonical agent guidance file; keep one source of instructions rather than adding a competing `agent.md`. Read relevant implementation and product documentation before changing a workflow; keep existing behavior unless the task explicitly changes it.

Start with `README.md`, `docs/mvp-status.md` and [the platform experience contract](docs/platform-experience.md). Inspect the working tree and actual route/API/schema before planning; dated checkpoints describe their recorded snapshot and do not override current source or the user’s instructions.

## Development and delivery

- Every cloud resource change must preserve `config/dev-power.json` and the Start/Stop development sequence. Run `python3 scripts/validate-dev-power.py`; new always-on resources need an implemented power action, and retained resources need an explicit cost/data rationale. ECS sidecars belong in the application task so they stop/start with it. Never use Terraform destroy for routine shutdown.

- `.codex/config.toml` records repository Codex defaults. Continue authorized, reversible implementation and validation without repeated confirmation; repository defaults do not override host sandbox/approval rules or authorize live, destructive or external actions. Apply the user’s existing authorization before asking again.
- Build and validate locally first. Keep the local preview browser open when the user wants to follow along; preserve their preview data when restarting services.
- Batch related feature, usability and performance work when requested. Do not merge, deploy, apply Terraform or change live configuration without authorization for that action.
- Keep changes focused and practical. Reuse established components and source records; avoid speculative abstractions, placeholder controls and invented data.
- Prefer the existing stack and shared components, then maintained free/open-source libraries that demonstrably reduce custom work. Additional services need a concrete benefit and expected operating cost; inexpensive AWS is preferred when a service is justified. Keep optional architecture/cache/schema pilots separate from workflow improvements unless their benefit is established. The planned complete API inventory, REST contracts and access-controlled OpenAPI/Swagger work remains tracked under PF-25.
- Delegate independent audit, implementation or validation when it improves coverage; assign clear file ownership, coordinate shared changes and resolve review findings before the final check. Keep one final validation record for the integrated result.
- Explain the result, validation and material limitations. Do not claim a local check proves cloud deployment or external email delivery.
- Keep work focused to control usage: read targeted files/diffs, batch independent checks, summarize browser state, and reuse valid test evidence. Repeat checks when changes or unresolved failures justify them. Do not silently widen a bounded increment into a redesign or another epic.

## Living feature register and completion

- Keep progress and validation notes local. Jira tracking is disabled by user preference; do not read, create, update or synchronize Jira unless explicitly requested. Existing issue keys/links are historical references only.
- `docs/product-roadmap.md` is the running feature/status register; `docs/product-backlog.md` holds detailed acceptance. Preserve stable PF IDs, completed capabilities and outstanding scope. Add an ID for genuinely new work; update the existing item for refinements.
- For each increment record the user outcome, real data/source records, role/property boundaries, next complete workflow, dependencies, validation and evidence. Distinguish proposed, in progress, local/PR, merged, deployed and user-accepted; unknown remains unverified. Never equate a passing test, navigation item or deployed release with acceptance.
- Build production-grade operating workflows: connected source/detail/history, correct complete totals, recoverable failures and drafts, concurrency/retry protection, useful audit history and measurable operations. No dummy features, invented production data, inactive controls or unsupported success claims. Clearly labeled fictional fixtures belong only in isolated preview/tests.
- A feature is complete when authorized users can finish its real job, follow sources and return with context, correct/reopen where appropriate, and understand the resulting state. Include owner/manager/resident projections and staff boundaries that apply; keep the UI clean and reveal richer details when useful.
- Keep release notes and the feature register current in each PR. Record migrations, activation variables/provider setup and remaining acceptance work; the user handles merge/deployment unless explicitly delegated.

## Feature delivery and documentation contract

- Before implementation, identify the user’s job, canonical entry/detail/source routes, affected roles, company/property boundaries and existing records/actions. Read the matching workflow contract and adjacent implementation. Extend the established workflow before inventing another page, menu item, status, data model or API for the same job. Every primary route must appear exactly once in `navigationSections` in `client/src/navigation.ts`; keep its placement regression passing as routes evolve.
- Follow `docs/platform-experience.md` for the platform’s visual language, navigation, forms and state behavior. Prefer existing components, CSS tokens and formatting helpers. Keep desktop, narrow-screen and keyboard workflows usable; do not solve a local layout problem with unrelated global overrides.
- Extend `client/src/design-tokens.css`, the baseline in `index.css` and the shared structure in `workspace-patterns.css`. Use semantic `--pf-*` colors, spacing and radii; keep workflow CSS scoped. Reuse `FormField`, `FormSection` and `FormActions` for labels, native requirements, associated help/errors and section navigation. Review shared changes in more than one adopting workspace and in real loaded, empty and unavailable states.
- Keep Search workspace and its Ctrl+K/Command+K results aligned with the canonical navigation/task metadata. Intersect role and company feature availability, identify read-only destinations, and preserve page results when property lookup fails. Preserve mobile drawer focus/scroll behavior and the source editor's leave guard when navigation is canceled. Property search does not imply tenant, lease or private-document search.
- Use the shared directory summary/filter/reset/paging anatomy and retain permitted property/source-return context. `useDirectoryPage`/`DirectoryPagination` are only for complete already-loaded arrays, filtered before slicing; keep server cursor windows and their actual total/page-count contracts intact. Users local filters cover synced accounts; Check exact email is the separate provider lookup. Do not relabel a partial provider list as the complete directory.
- Declare each form's query, review or write intent and use wording that matches its result. Preparing a review is not a completed mutation; filtering must not report a saved business record. Gate each new operation with its actual role and feature write mode. Same-authority read-only refresh may lock an existing editor without dropping its values or original submitted request/key; actual actor/company/authority changes must retain the established privacy boundary. Never clear another editor's dirty/busy state when one operation settles.
- An unfinished cross-editor handoff needs an explicit owner: retain exact unsubmitted values and leave/unload protection until the destination has mounted its own dirty guard and acknowledged that same handoff. Keep retry, return and discard scoped to it; preserve older uncertain reviews and other forms' registrations. Hide private values on read denial and clear them on an actual actor/company/authority change. Do not mark a whole page complete when only one source form transferred its values.
- Define completion with observable acceptance: who starts where, what real action succeeds, what resulting state/history appears, and how the user returns or continues. Include the relevant empty/loading/error/permission-denied, stale-edit, retry and interruption states. Describe unsupported provider or role behavior explicitly.
- Update documentation in the same change as behavior. Use the change-to-document map in `docs/platform-experience.md`; review the changed route labels, permissions, form fields, source links, errors and recovery behavior against the affected contract. Update `client/src/help-content.ts` when user instructions change. Correct obsolete current statements instead of stacking a contradictory new checkpoint above them.
- Keep `docs/mvp-status.md` concise and current, `docs/product-roadmap.md` as the stable PF feature register, `docs/product-backlog.md` as outstanding acceptance, and `docs/local-feature-release-notes.md` as dated delivery evidence. Preserve original dated logs; link to them instead of copying old counts into current claims. Record docs that need no update with a reason in the handoff when that decision is material.
- Validate the complete changed path, including direct URL/reload/back/return navigation and applicable role projections. Add meaningful regression coverage for demonstrated correctness, authorization or recovery defects. Report exact commands/results and unverified dependencies; never turn an old passing run into evidence for changed code.
- Use `.github/pull_request_template.md` when preparing a PR; complete its workflow, experience/docs and validation sections with actual evidence rather than checking boxes by assumption.
- Before handoff, inspect the final diff for duplicate navigation, conflicting terminology, stale help/docs, exposed private data, inactive controls and drift from adjacent screens. Report changes, checks, remaining scope and deployment/acceptance state. A checklist supports review; it does not establish that every bug is fixed or that live workflows are accepted.

## Sales demo maintenance

- Review the sales demo whenever an implemented feature, schema, validation, source link or workflow changes. When the represented fixture or source relationships change, update `server/src/sales-demo-seed.ts` and `server/src/sales-demo-scenarios.ts`, bump `SALES_DEMO_SEED_VERSION`, keep `DEMO_FEATURE_COVERAGE` and `DEMO_PRESENTATION_STOPS` accurate, and update the blueprint, walkthrough in `docs/sales-demo.md` and lifecycle regression. Include meaningful absent/pending/corrected/archived states, especially tenants without portal access or sign-in, rather than only successful active accounts. The coverage regression must continue to cover every shipped company feature-catalog entry. For a presentation-only refinement that needs no fixture change, record why the existing fixture/source coverage remains valid.
- Keep blueprint inspection read-only. The UI/operator workflow requires reviewing the blueprint before a new build and reviewing a lifecycle action plan before teardown or fixture update/fresh rebuild. New tooling must send the reviewed hash; the legacy-compatible create/teardown API still accepts an omitted hash, while rebuild requires its hash and explicit confirmation. Do not describe operator review as a universal backend gate. Confirm the original source/version, plan hash, fixture and pinned environment/date assumptions before writes. Rebuild reserves one durable successor, retires the exact reviewed generation through its lifecycle, then builds the fresh dedicated company/accounts; resume its unfinished setup instead of starting another generation. Refresh stale plans before confirmation, and preserve the original request while a submitted result is uncertain. Never silently rebase a reserved setup or rewrite an old generation's posted history. Follow `docs/sales-demo.md` for recovery and changed-source blockers.
- Fictional data is permitted only in explicitly labeled, dedicated sales-demo companies and isolated preview/tests. Demo setup must use connected source records and existing business handlers, company context/RLS, atomic source/audit writes and durable retry identity. Never copy customer data, reassign an occupied account, seed production plan prices, send external messages or move money. Automatic Auth0 provisioning is the implemented behavior specifically for generated demo accounts; normal account verification and setup rules remain unchanged. This feature contract does not itself authorize an agent to execute live provisioning, retirement or rebuild; apply the current task’s action authorization.
- Demo creation must provision usable owner, manager, staff, resident/leaseholder and occupant logins automatically, with unique generated emails/passwords, exact Auth0 issuer/subject mappings and demo-only verified-email creation. Never adopt or reset unrelated identities by email. Keep provider calls outside database transactions and persist resumable generation ownership before making them. Demo passwords are encrypted at rest and revealed only through freshly authorized, audited, no-store platform operations; never log them or put them in ordinary lists, telemetry, browser storage or Git. Teardown disables generated local/Auth0 accounts and revokes sessions while retaining source/history; older version-one demos preserve their pre-existing presenter identity. Test provider recovery, every role boundary, teardown/rebuild and customer isolation with `node scripts/test-sales-demo.mjs` on a fresh disposable database.
- Prepared offline/pending/former tenant identities have no issued credentials or portal membership. Preserve the distinction between account preparation, contact/lease history, invitation, portal grant and first sign-in. Document examples must use the same supported-type/size validation and explicit unscanned status as ordinary uploads. Malware scanning was removed at the user’s request; never invent a clean verdict or change historical scan results, and keep known rejected originals blocked.
- Demo identity calls must pace requests, respect Auth0 cooldowns and retry within the operation budget. Resume must continue from durable issuer-bound confirmed subjects without replaying completed account lookups (revalidate older unbound snapshots once through the paced provider); keep ambiguous-create recovery and fresh local assignment checks. Cover rate limits late in setup, unchanged credentials, provider cleanup and bounded retries in the lifecycle/provider regressions.

## Product and interface

- Properties, units, tenants, leases and maintenance form connected workflows. Preserve context and offer clear next actions from actual record state.
- Show setup prompts only for missing setup. Account creation happens before new tenant/lease participation; portal activation and first sign-in remain separate.
- Make directories useful for daily work: meaningful labels, property/unit context, search, clear status and direct detail links. Keep secondary and archival actions unobtrusive.
- Forms must be readable and easy to navigate, with grouped fields, useful detail, clear required/optional labels, validation and preserved input after errors.
- Display dates with the month name, day and year. Group postal addresses as street, then city/state/postal code. Keep dates, currency and status wording consistent.
- Use responsive layouts, semantic controls, visible focus, accessible labels and explicit loading, empty, error and success states.

## Identity, authorization and history

- Auth0 is the account authority. New tenants and every new leaseholder/occupant require an existing or precreated account. Use the existing User + exact Identity mapping; contacts and invitations reference that account. Account existence, contact email, a profile or a lease record never grants portal access by itself.
- Keep profile, platform authority, company membership, property access and lease participation distinct. Identity is keyed by issuer/subject, never automatically linked by email.
- Leaseholders may see authorized shared lease finances; occupants have no financial access. Owners approve resident additions/removals. Emergency contacts are separate from household members.
- Staff default to read-only property access. An explicit owner grant may add maintenance execution only within current property scope and assignment; it grants no finance, lease, team or document authority. Residents may edit permitted personal details, never their own company role, property/unit assignment, lease terms or access grants.
- Authorize each API operation from fresh server-side membership and permissions. Treat route IDs and `X-Company-ID` as untrusted input.
- Property data operations use transaction-local company context, explicit company filters and existing row-level security. Platform authority does not bypass company boundaries.
- Preserve financial source IDs, signed/posted history and immutable audit events. Record consequential changes atomically; use version checks and durable submission keys where retries or concurrent edits could duplicate or overwrite work.
- Browser calls use `client/src/api.ts` and server-managed cookies/CSRF. Never request OAuth tokens in page components or expose provider/client secrets in logs, responses or artifacts. The explicit demo-credential operation above is the sole generated-password response exception.
- Read `docs/access-overhaul.md` for access/deployment boundaries and `docs/open-observability.md` for current Grafana monitoring; historical Datadog instructions are superseded.

## Stack and validation

- Client: React/Vite/TypeScript. Server: Fastify/Prisma/PostgreSQL. Identity: Auth0 OIDC. Follow adjacent conventions and keep database migrations additive where practical.
- Client build: `npm run build --workspace=@property-flow/client`.
- Server build: `DATABASE_URL=postgresql://build:build@127.0.0.1:1/propertyflow_access_test npm run build --workspace=server` (Prisma generation and compilation; no database connection).
- Safe units after building: `node --test server/tests/*.test.mjs` and `node --test client/tests/*.test.cjs`, with integration database variables unset.
- Operations checks: `python3 -m unittest discover -s tests/operations -p 'test_*.py'`.
- Use existing disposable database runners for integration tests (`scripts/test-maintenance.mjs`, `scripts/test-finances.mjs` and related runners). Never point tests at development/customer data.
- Use the existing browser fixture suite for UI regressions and verify changed flows in the local preview. Run checks appropriate to the change; add meaningful coverage for authorization, data integrity and consequential behavior.
- Use `node scripts/local-validation.mjs plan` for changed-area feedback guidance, then the normal-build receipt and complete fixed production suite described in `docs/agent-validation.md`. Plans do not reduce CI/release gates. Cache only verified unchanged builds, never test results or databases; witnessed environment overrides get a one-use fresh-only receipt, while unsupported custom dependencies remain blocked. Preserve inherited trust/env settings and never substitute a compile-only server artifact for normal Prisma generation.
- Keep source and build fixed during browser validation. Run local database/browser runners sequentially and finish Docker cleanup before the static-client suite; independent ports/databases do not prevent global network-interface interruptions. Retain failure traces, diagnose transport versus product failures, and correct the cause without automatic full reruns, retries or weakened assertions. Follow the validation guide for EC2 CLI prerequisites and portability; no secret-file or temporary database handoff is implied.
- Monitoring must accompany shipped workflows: bounded outcome/duration/failure signals, safe logs/traces and an actionable alert/runbook when needed. Preserve RUM privacy; never capture private form/contact/financial data or enable replay implicitly. See `docs/monitoring-coverage.md` for remaining coverage and activation evidence.
