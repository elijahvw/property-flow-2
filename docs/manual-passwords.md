# Administrative password setting

Platform owners can open **Platform → Users → Manage → Sign-in & status → Set password manually**. Company owners can choose **Team → Manage password**, or the control in an active resident member's **Tenant details → Account & portal access**. The review identifies the exact existing account. Enter and confirm the new password, then choose **Set account password**. This does not create an account, verify its email, reactivate it, or grant company/property/portal authority.

Only active accounts with the exact configured Auth0 issuer/subject and matching Auth0 database connection support this action. Social/federated sign-in accounts retain their provider's password workflow. The provider applies its configured password policy; the local form requires matching 8–128-character entries. Property Flow does not request a reset email; separately configured Auth0 actions may have their own effects.

A platform owner can manage these existing accounts platform-wide. A company owner can manage only current active members of that same active company whose account has no platform authority. A tenant contact, email address or prepared offline account alone does not grant authority over a global sign-in account. Platform-support-only users, managers, staff and residents cannot use the administrative password operation. Setting one's own password revokes the current Property Flow session as well; sign in again to continue. Impersonation remains read-only.

## Review, provider work and recovery

Migration `202610260059_manual_passwords` adds a password-change receipt and `User.credentialChangedAt`. The API rechecks current actor/target authority, exact identity, record timestamp, company membership/version and account status against the reviewed context. CSRF and a bounded request rate apply. Identity-provider work occurs outside database transactions.

A committed intent reserves that exact account against concurrent new access grants/transfers and demo cleanup. A platform owner may still disable the account; historical-attempt recovery remains available for that disabled target. Request fingerprints use HMAC under a separate HKDF purpose derived from the existing application secret, including actor/account/review/password. Passwords themselves are not written to the database, audit, logs, telemetry, browser storage or generic draft/retry journals. The app needs no new provider scope beyond its existing `update:users` management capability. The same confirmed request returns its saved receipt without repeating a provider password write. A released/finished receipt is never overwritten by an older delayed provider response; late finalizers cannot reactivate its reservation, replace a newer outcome, or revoke newer sessions.

Immediately before dispatch, one transaction records the dispatch audit, invalidates older generated-demo credential sheets and revokes normal/impersonation Property Flow sessions for the target. The server submits the password only to the pinned Auth0 subject and database connection, with an absolute operation deadline. It records the confirmed result and audit atomically. A request/lookup/provider rejection never becomes an invented success.

After an interrupted or unconfirmed result, password fields are cleared. Choose **Check attempt status** to read the durable result using the original submission key. A pending/unconfirmed attempt cannot be automatically resent. After the displayed review time, **Release reviewed attempt** acknowledges the unknown result and releases the reservation so an administrator may review and enter a fresh password. Release is not proof that the previous password worked. Platform administrators can resolve another authorized administrator's abandoned attempt within the same target scope; the release audit retains the original intent's company scope and identifies the releasing actor and operation. Target scope remains freshly authorized throughout recovery. A platform owner can inspect/release an expired historical attempt even when its user is disabled, its identity mapping changed, or the provider connection is unavailable. Those conditions disable new password writes; they do not strand a local recovery receipt. Company owners retain their current active same-company, non-platform-member boundary.

A provider success followed by a local receipt failure stays unconfirmed and recoverable; it is not reported as applied without the atomic completion audit. Earlier generated role-password sheets stay unavailable once dispatch begins, including after ambiguous provider responses. Demo teardown still requires exact generation/provider ownership and waits for any pending password attempt to be resolved. No posted demo/source history is rewritten.

## Interface and validation

The password form is separate from generic save/draft forms. Fields clear after every attempt, on close and when actor/company/authority changes. Password controls are excluded from editor draft snapshots. A hidden or closed user editor cannot keep a password form alive; pending writes hold the existing editor busy guard. Sensitive values never enter operation telemetry; only `account.password.set` outcome/duration is recorded.

Regression coverage includes platform/company role boundaries, cross-company and platform-target denial for company owners, exact database identity, bad input/CSRF/stale review, intent/audit rollback, concurrent dispatch and account-change reservation, no password retention, session revocation, confirmed receipt replay, ambiguous provider result, explicit delayed release, and a provider success whose completion audit fails. Live password policy, Auth0 actions and real-account sign-in remain deployment acceptance work; no live password change is established by disposable fixtures.

Provider contract: [Auth0 password changes](https://auth0.com/docs/authenticate/database-connections/password-change) and the [Update a User API](https://auth0.com/docs/api/management/v2/users/patch-users-by-id). Local fixtures do not establish a tenant’s actual policy or Action behavior.
