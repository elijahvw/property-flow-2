# Current account policy — October 17, 2026

The user replaced the optional-account policy below. New tenants and every new lease participant require one Auth0 account, prepared from Property Flow before recording their participation. Existing User + exact Identity issuer/subject remains the only account representation; ResidentContact stores company-owned business details and references that account through userId. Invitations reference the same existing account through accountId; they are access/onboarding records, never another account type.

Auth0 creation/reuse happens under fresh management authorization before the final scoped transaction. The local mirror, contact/lease writes and audit commit together. External provider creation cannot share the PostgreSQL transaction; a later local rejection can leave an unassigned Auth0 account, which a retry reuses. A possible-duplicate review occurs before contacting Auth0 and is rechecked at commit. Multiple identities for an email require explicit account review, never automatic merging. Current exact subject bindings take precedence over correspondence email. Account existence grants no membership, property access or financial authority.

Owners can send password-reset email from tenant details; platform owners can do so from Users. Resets resolve the stored issuer/subject and current provider email, cannot accept a caller-selected recipient, enforce cooldown/disabled checks, and never create accounts. Existing social/enterprise accounts use their own sign-in provider. Database onboarding sends one password setup email, which also verifies the address; no redundant verification email is requested. See [sign-in settings](auth0-sign-in.md).

Legacy unbound contacts and financial history are retained without bulk Auth0 creation or email matching. The next authorized lease/household/invitation operation prepares their account, requiring an email when missing. Prior accepted records and removed participants are not rewritten. Existing memberships and approvals continue to gate portal access. No production accounts or provider settings have been modified by local validation.

Migration 202610170030_resident_identity_accounts adds the nullable Invitation.accountId foreign key/index and an immutable target guard. Apply it with the matching server before new invitation writes. The old binary can read the additive schema, but rolling back the server can restore the old delayed-account behavior. Do not drop account/identity/history rows on rollback. Local preview uses a clearly simulated provider and never sends live email.

The sections below document earlier shipped increments and their original policy; this current policy supersedes statements that a new participant can remain accountless.

# Offline tenant contacts: identity, recording and optional portal access

This is the first reviewable slice of PF-03, based on merged PR #34 / main `0e492f8`. The user reports #34 deployed. The [backlog](product-backlog.md) splits contact identity/backfill, offline contact and lease forms, and verified portal linking into separate reviews.

## Implemented contract

`ResidentContact` is a company-owned business identity with a name, optional email/phone, emergency contact and management notes. Its optional `userId` maps an existing account by its exact stored identifier. This mapping grants no membership, property assignment, portal permission or financial access. No identity-provider users or invitations are created by this bridge.

Migration `202610160017_resident_contacts` runs in an explicit PostgreSQL transaction. It backfills current resident memberships and historical lease/household identities, using a distinct contact for each company/User pair. It copies membership contact/private fields only from that same company's membership, including a former resident now assigned a staff/manager role when lease history establishes the contact. A transferred person's current company's notes cannot populate their former company's contact. Original identity names/emails are bounded display snapshots; the original User and membership fields remain intact.

Unlinked household records receive separate contacts, even when their names or emails match each other or a linked account. There is no automatic deduplication or merge. Previously recorded unlinked residents in different leases remain distinct because their common identity has not been reviewed. New renewal drafts reuse the source participant's contact ID; they still require the existing explicit owner portal approval. A null bridge left by an earlier-version rollout is filled on its source roster before copying; transferred accounts use the historical roster snapshot and receive no new access.

Leases gain `residentContactId`; household participants gain `contactId`. Composite foreign keys keep both within their company. Existing lease, User, participant, rent, receipt, allocation, deposit, reference, submission, version and audit identities remain unchanged. Neither household size nor the new contact table changes the shared financial obligation.

New application membership, lease, household and accepted-invitation writes create/reuse contacts in their existing serializable transactions. Retries reuse the committed source and contact. Profile edits update the membership compatibility fields and contact together; an audit failure rolls both back. Household edits remain lease-specific for linked and record-only participants; independent source/renewal participant versions cannot overwrite shared contact details. Company profile edits update linked contact details. A dedicated versioned contact editor follows with PF-03b. Removing a participant, disabling access or transferring a membership retains contacts and money history. Before a transfer or role/ownership change, a private compatibility-profile snapshot detects fields edited by the previous application during rollout. Only changed source fields are reconciled into the departing company's contact, preserving independently curated fields whose compatibility values have not changed. Transfers then clear membership private fields and create/reuse the distinct target-company contact.

Contacts have forced company RLS, explicit transaction company context and restricted runtime grants. Runtime cannot delete contacts or update their company/User identity mapping. Existing current membership, verification, role and property/lease authorization remains the source of portal authority. The additive contact IDs are returned only in existing management lease/household responses; contact private fields are not added to bootstrap, platform user lists, tenant finances or invitation preview.

## Rollout and compatibility

Bridge columns remain nullable so the previous application can continue operating during coordinated rollout or application rollback. Previous-version writes can leave bridge IDs null; the next contact workflow slice must resolve these legacy rows before requiring contact identities. This increment does not switch existing routes or client payloads to contact IDs and does not expose a new contact linking endpoint. Old durable submission fingerprints remain valid.

Deploy through the existing user-run migration/backend workflow after review. Preserve a database restore point as usual. The previous app may run against the additive schema; do not drop contacts or bridge columns after new writes. Prefer a forward fix. Transaction rollback during a failed migration is distinct from deleting an applied migration or reversing later business activity. A failed Prisma migration still requires normal operator review/resolution before retry.

## Original PF-03a release boundary (superseded by PF-03b below)

PF-03b will make contacts the tenant directory/detail and primary lease selection source, allow an owner/manager to record an offline tenant and lease/manual rent/deposit, and adapt every management/report/household projection to a primary contact without a User. It needs focused readable forms, useful contact detail, month-name dates, review, durable recovery and clear next steps. It will retain existing User-based URLs as compatibility entries.

Verified portal invitation/linking follows separately: explicit intended-contact selection and owner approval, recipient preview, verified matching acceptance, concurrency/revocation checks and conflicts for existing membership elsewhere. Email matching alone cannot grant authority, merge contacts or combine financial liability. Contact archive/search policy belongs with the directory transition. No multi-company membership expansion is implied.

This foundation does **not** yet let an offline contact be the primary leaseholder. Existing primary tenant selection still requires an eligible account; additional record-only household residents continue working. It contains no new form redesign, infrastructure/provider change or deployment.

## PF-03b: profile-first recording and optional portal access

The follow-on implementation starts from merged/deployed PR #35 (`47be1cf`). At the user's explicit request, this slice also connects invitations to saved profiles instead of deferring portal linking to another increment. Every recorded tenant/household resident has a company-owned profile; a login is optional. A verified account has at most one profile in a company, and a person still has one current company membership. Contacts and accounts are never merged by email.

Owners/managers can add a tenant with a name alone, contact preferences, phones, mailing address, emergency relationship/details and private notes. The directory searches contacts and distinguishes not invited, pending, verified/active and disabled portal access; archived profiles remain searchable. Review/save uses scoped drafts, version checks, durable submission keys and an explicit duplicate-person confirmation. Archive retains records and money history and refuses current lease relationships. Existing account-based detail URLs remain supported.

Primary leases now accept a contact without a User. Management lease, rent, deposit, report and household projections resolve the contact name without manufacturing a sign-in account. Posted financial source IDs, amounts, allocations, revisions and audits are preserved. Recording a contact-based lease for an active linked resident explicitly connects their current company account to that property; the lease review explains this. Disabled/transferred accounts remain ineligible. A renewal reuses the same profiles, retains all old money sources and requires review of copied additional leaseholders.

A profile or household form offers **No: keep a profile for tracking** or **Yes: review access and create an invitation link**. Owners approve the exact profile and current leaseholder/occupant scope. Links are shown for explicit sharing, not emailed automatically. The invited person can request Auth0 password/verification emails from the private landing page before sign-in, then accepts using the matching verified account. This uses the existing identity-provider configuration and does not enable public signup. New lease-specific invitations save their approved tenant profile before acceptance and reuse it when the account joins. Unapproved resident requests remain owner approval requests. Older links remain compatible.

Acceptance fences company/owner/account/contact/household changes, rejects foreign or disabled memberships and duplicate account/profile mappings, and links the exact saved profile. Leaseholders receive shared lease balances; occupants do not receive lease financial access. Pending household/term changes require a freshly reviewed contact invitation. Accepted-token replay acknowledges only; it cannot restore revoked assignments or removed residents. Updating contact email or archiving revokes pending profile invitations. Revocation preserves profiles/history.

The same increment adds explicit **No company access** in platform user management, with stale-assignment and last-owner checks. Removing membership preserves the application profile and company contact history. Deployment no longer offers or executes Datadog retirement; the separately invoked guarded cleanup script remains available for reviewed operational recovery.

UI audit: property, company and tenant addresses use street lines followed by city/state/postal code together. Property location is a readable block separate from building metadata. Tenant/household forms use bounded columns, full-width address lines, grouped optional details, month-name date fields, review and visible next steps. Desktop/mobile browser screenshots validate reading order, overflow, private-token removal, retry recovery and profile-first invitation controls.

Release: apply additive migration `202610160018_offline_tenants` with the matching server and client. It catches up missing contact bridges written by the prior binary, permits a nullable legacy primary User with a required contact/User identity, adds profile/invitation fields, and permits one-time null-to-account linkage while database triggers retain existing non-null mappings. Keep a database restore point and use a coordinated release; after creating offline primary leases, reverting only the application to a binary that requires every primary User is not safe. No live/shared database, Auth0 configuration, account, email, infrastructure or deployment was changed during local validation. Actual provider email delivery still requires deployed acceptance testing.
